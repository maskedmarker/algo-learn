# 限流算法


## 令牌桶算法（Token Bucket）

```text
令牌桶算法（Token Bucket）核心逻辑

一句话总结:
系统以固定速率往桶里放令牌，请求必须先拿到令牌才能执行；桶满了令牌就不再增加(溢出)，可应对突发流量(初始桶内加满)。

桶满了令牌就不再增加: 通过溢出实现
应对突发流量: 通过初始桶内加满, 空闲时桶内可容纳暂没消耗的令牌.

时间驱动自动漏水: 不需要独立线程定时放令牌，通常在每次请求时,根据「当前时间 - 上次更新时间」计算这段时间应生成的令牌数.把令牌加入桶中，不超过最大容量。
```


## 漏桶算法（Leaky Bucket）

```text
漏桶算法（Leaky Bucket）核心逻辑

一句话核心:
请求像水一样倒进固定容量的桶里，桶以恒定速率匀速往外漏水（处理请求）。当水满时，再进来的水会溢出，即直接被拒绝限流。


时间驱动自动漏水: 核心机制是时间驱动，而非主动线程。每次新请求到达时，会先计算自上次漏水以来经过的时间，并按速率扣除相应水量，更新桶内剩余水量(即还可以申请的请求数量)。
```

## 令牌桶算法与漏桶算法 比对

```text
漏桶算法与令牌桶算法的关键区别


特性	        漏桶算法 (Leaky Bucket)	            令牌桶算法 (Token Bucket)
控制方向	    控制流出速率，匀速处理	                控制流入速率，可积攒令牌
突发支持	    ❌ 不支持，必须按固定速度处理	        ✅ 支持，可一次性消耗桶内所有令牌
核心比喻	    水从桶底固定孔流出，速度恒定	            按固定时间往桶里丢令牌，拿到令牌才能通过


令牌桶算法的桶内容纳的是当前可用许可;漏桶算法的桶内容纳的是当前正在执行的请求.
限流算法不仅要知道系统令牌生成速率,还要记录当前系统状态.令牌桶算法选择记录当前可用可用许可,漏桶算法选择记录当前正在执行的请求.
可用许可是可以暂存的,请求的暂存只能是排队等待.
```

## 容量与TPS

```text
漏桶算法的容量与TPS


如果要求 TPS = 100/秒

1. 速率决定 TPS
漏桶算法里：
漏水速率 = 系统每秒能处理的请求数 = TPS
所以要 TPS=100，必须设置：漏水速率 = 100 请求/秒
这是硬性规定，和容量无关。

2. 容量决定什么？
容量 = 桶最多能装多少请求作用只有一个：控制允许的突发排队量
（1）容量 = 1
只能一个接一个匀速进,完全不允许任何突发,多来一个直接拒绝,最严格、最平滑
（2）容量 = 100（最常用）
允许瞬间最多突发 100 个请求进来排队,之后仍然以 100 TPS 匀速处理,既平滑流量，又能抗一点突发
（3）容量越大
允许的突发排队越多,处理速度永远是 100 TPS,太大容易占内存、请求排队延迟高

最终推荐配置（标准工程用法）
漏桶速率：100个/秒（控制 TPS）
漏桶容量：100（允许一秒的请求量做缓冲）

如果你想要：
完全无突发、绝对匀速 → 容量 = 1
能抗瞬间小峰值 → 容量 = 50~200
网关/强抗突发 → 容量 = 300~500（但处理速度仍 100 TPS）
```

```text
令牌桶算法的容量与TPS


如果要求 TPS = 100/秒

要求 TPS = 100（每秒稳定 100 请求）
令牌生成速率 = 100 个/秒（决定平均 TPS）
桶容量（burst size）建议 = 100（决定最大突发量）


速率控制平均TPS
每秒放 100 个令牌 → 长期平均 TPS 就是 100，这是固定的。


容量控制「突发量」
桶容量 = 系统最多能一次性扛多少突发请求。
容量 = 100：系统空闲时，桶会攒满 100 个令牌，瞬间来 100 个请求可以全部一次性通过，之后就只能按 100 TPS 匀速通过。这是最标准、最常用配置。
容量 = 1：完全不允许突发，和漏桶效果一样，只能一个一个匀速过。
容量 = 200：允许瞬间突发 200 请求，之后仍然按 100 TPS 匀速。


通用配置原则（行业默认）
限流 TPS = N
令牌生成速率 = N
桶容量 = N（允许一秒的请求量作为突发）
```
